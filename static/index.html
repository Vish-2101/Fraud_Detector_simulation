FROM THEORY TO A WORKING MODEL

Open the black box.

Inspect the actual algorithms behind this academic simulation.

Implemented here: exact sliding windows, weighted rules, Apriori, DGIM and Bloom Filter. The score is a heuristic rule score, not a trained ML model or a probability.

01 · Exact sliding window

Decision feature

Each arriving event updates per-device, IP and card counters. Events at or before now - 60s expire. The current event is included.

Event→Expire old→Update counts→Score

Distinct-account counts use reference counts, so multiple events from one account are not counted as multiple accounts.

Expected O(1) keyed updates; expiry is amortized O(1) per event. History capped at 2,000 events. DGIM below estimates the same bursts without storing the full window.

A · Apriori: signals that occur together

Offline analysis

Level-wise candidates with subset pruning on event signal baskets (only indicators that fired). Max itemset size 3.

Support = share of analyzed events containing the itemset. Confidence P(B|A) and lift are shown per rule. Co-occurrence is not causation and high support does not prove fraud. Baskets are rule-derived, so patterns can be circular; Apriori never scores events.

B · DGIM: suspicious bursts in last N events

Streaming estimate

Binary stream per device/card: 1 when an event carries failed, disposable-email or country-mismatch; else 0. Classical buckets (powers of two, max 2 per size). Window = last 60 stream elements per entity (about 60s only under 1-event-per-second playback).

BUCKET POSSIZE

Estimate = sum(bucket sizes) minus half the oldest (boundary) bucket, so it may differ from the exact count. A qualifying estimate adds a modest +10 dgim_device_burst only with corroborating evidence; DGIM alone cannot block (max +20 below review).

C · Bloom Filter: possibly seen before?

Probabilistic membership

Separate filters for device and card identifiers (synthetic aliases only). Query before insert: first sighting reports definitely_absent; later sightings report possibly_present (may be a false positive, never proof of fraud).

No identifiers yet

Deterministic BLAKE2b hashes (3) over 512 bits. Insert-only: expiring exact counters does not clear bits; Reset clears the session. A positive contributes at most +10 and only when corroborated (reuse/trial/disposable/failure).

READY FOR YOUR CLASSROOM DEMO

Tell the story in five minutes.

Show the problem, expose the evidence, then discuss the trade-offs.

Presentation walkthrough

  1. Start with normal traffic. Reset, choose Everyday payments and run. Ordinary events stay low risk.
  2. Introduce card testing. Repeated attempts on the same card raise velocity. Select a blocked event to explain the points.
  3. Demonstrate free-trial cycling. Reused devices, multiple accounts, trial starts and cancellations build evidence over time. Early abuse can escape detection.
  4. Test shared campus Wi-Fi. Distinct users share a network but not a device. IP reuse contributes only 10 points and alone stays allowed under the default thresholds.
  5. Explain false positives and negatives. Reset and run Mixed traffic. Legitimate travelers can be flagged; a stealth attack can be missed. Change the review threshold and watch precision and recall.
  6. Connect to the syllabus. Open Algorithm explorer. Compare exact window counts with DGIM estimates, test Bloom reuse, explain Apriori support/confidence/lift, and advance 61 seconds to show exact-window expiry (Bloom persists, DGIM is count-based).

What the model does

A Python service consumes synthetic payment and account events, maintains a 60-second window, applies transparent weighted rules and returns allow, review or block. The browser animates the stream. Events and metrics are real computations, not pre-rendered results.

What to say accurately

“This is our educational simulation inspired by the business problem in Stripe Radar. It demonstrates stream mining and explainable heuristics. It does not reproduce Stripe’s proprietary machine-learning model, production thresholds or infrastructure.”

Review here is a generic analyst/verification recommendation. It does not simulate payment capture, issuer authorization, 3-D Secure, actual credit restriction or Stripe’s payment-review semantics. Labels describe authored scenarios, not independently observed fraud outcomes.

Advantages & limitations

Incremental counters are fast and easy to explain. Rule weights are manually chosen and can miss attacks or flag legitimate users. Device aliases can be rotated; real identity resolution is absent. Bloom filters and DGIM trade exactness for fixed/streaming-friendly state, while Apriori can become costly as the item vocabulary grows. A production system needs validated predictive models, real outcome feedback and distributed state.

AI-use disclosure

Codex assisted with implementation, interface design and tests. Students should review the rules, run the demonstrations, understand the limitations and describe this assistance in the assignment’s AI declaration.

Scope of your report

CURE, GSP, exponential histograms and DTW are discussed as possible academic alternatives in the supplied report; they are not implemented in this model. The cancellation-to-trial signal here is a simple window rule, not GSP.
